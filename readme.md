# PostgreSQL Data Modeling Tutorial (Docker + pgAdmin)

## Overview

In about 45 minutes you will run PostgreSQL 17 and the pgAdmin GUI in Docker, then design a small neighbourhood grocery store database (customers, products, bills) by clicking through pgAdmin and by writing the equivalent SQL.

### The real-life picture

Imagine a neighbourhood grocery store (a kirana shop) that keeps its records in paper notebooks. A database is the same idea, with each notebook becoming a table and each line in the notebook becoming a row.

| Notebook in the shop | Table in Postgres | One row is |
| --- | --- | --- |
| Customer register | `customers` | one regular customer |
| Shelf price list, grouped by aisle | `products`, `categories` | one item on the shelf |
| Bill book | `orders` | one bill handed to a customer |
| Items written on each bill | `order_items` | one product and its quantity on a bill |

When a customer buys milk, the shopkeeper writes a new bill and adds lines to it. In section 5 you will do exactly that with a real-looking dataset of 8 customers, 10 products and 12 bills.

You need Docker with Compose v2 (Docker Desktop on Mac/Windows, or Docker Engine on Linux) and a browser. No local Postgres install is required.

By the end you will have:

- A running Postgres + pgAdmin stack you can throw away and recreate with one command
- A normalized schema with primary keys, foreign keys, unique and check constraints
- A one-to-many relation (customer to orders) and a many-to-many relation (orders to products)
- An entity-relationship diagram (ERD) generated by pgAdmin from the live database
- Sample data and joins that prove the model works

## 1. Start Postgres and pgAdmin with Docker

One `docker-compose.yml` starts both containers; pgAdmin is the GUI and is served at http://localhost:5050.

Create a folder (for example `pg-modeling`) and save this as `docker-compose.yml`:

```yaml
services:
  db:
    image: postgres:17
    container_name: pg_modeling_db
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app_pw
      POSTGRES_DB: shop
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 5s
      timeout: 3s
      retries: 10

  pgadmin:
    image: dpage/pgadmin4:latest
    container_name: pg_modeling_pgadmin
    environment:
      PGADMIN_DEFAULT_EMAIL: admin@example.com
      PGADMIN_DEFAULT_PASSWORD: admin_pw
      PGADMIN_CONFIG_SERVER_MODE: "False"
      PGADMIN_CONFIG_MASTER_PASSWORD_REQUIRED: "False"
    ports:
      - "5050:80"
    volumes:
      - pgadmin_data:/var/lib/pgadmin
    depends_on:
      db:
        condition: service_healthy

volumes:
  pgdata:
  pgadmin_data:
```

Start it:

```bash
docker compose up -d
docker compose ps          # both should show running; db shows healthy
```

Setting `PGADMIN_CONFIG_SERVER_MODE` to `False` runs pgAdmin in single-user desktop mode, so there is no login screen. These passwords are for local learning only; change them for anything shared.

### Connect the GUI to the database

1. Open http://localhost:5050.
2. Right-click **Servers** in the left tree, then **Register > Server...**
3. **General** tab: Name = `shop-local`.
4. **Connection** tab: Host name/address = `db` (the Compose service name, not `localhost`, because pgAdmin runs in its own container), Port = `5432`, Maintenance database = `shop`, Username = `app`, Password = `app_pw`. Tick **Save password**.
5. Click **Save**. Expand **shop-local > Databases > shop > Schemas > public**.

## 2. Data modeling in five ideas

A good model comes from answering four questions in order: what things exist, how do they relate, what identifies each one, and where does each fact live exactly once.

| Idea | What it means | In our store |
| --- | --- | --- |
| Entity | A thing you store facts about; becomes a table | customer, product, order |
| Attribute | A fact about an entity; becomes a column | customer email, product price |
| Primary key | Column(s) that uniquely identify a row | `customer_id` |
| Foreign key | A column that points at another table's key; enforces the relationship | `orders.customer_id` references `customers` |
| Cardinality | How many rows on each side of a relationship | one customer has many orders; one order has many products and a product is in many orders |

### Normalization in plain words

- **1NF:** one value per cell, no repeating groups. Do not store `products = 'pen, ink, pad'` in an order row.
- **2NF:** every non-key column depends on the whole key. In an order line keyed by (order, product), the product name belongs in `products`, not in the line.
- **3NF:** non-key columns depend only on the key, not on each other. Do not store both `zip` and `city` if zip determines city; split them out.

The practical rule: store each fact once, and link rows with keys. Denormalize later, on purpose, only when a measured query needs it.

### Choosing data types

- Money: `numeric(12,2)`, never `float`, which rounds.
- Timestamps: `timestamptz`, which stores an absolute moment and avoids time-zone bugs.
- Surrogate keys: `bigint GENERATED ALWAYS AS IDENTITY` is the modern replacement for `serial`.
- Short fixed vocabularies (order status): a `text` column with a `CHECK` constraint is simple and easy to change; a Postgres `ENUM` is harder to alter.
- Text: use `text`; in Postgres `varchar(n)` gives no speed benefit.

## 3. Build the schema in pgAdmin

The model has five tables: `categories`, `products`, `customers`, `orders` and `order_items`. `order_items` is the junction table that turns the many-to-many link between orders and products into two one-to-many links.

### Create your first table with the GUI

1. In the tree, expand **shop > Schemas > public**, right-click **Tables**, choose **Create > Table...**
2. **General** tab: Name = `customers`.
3. **Columns** tab: click **+** and add:
    - `customer_id`, type `bigint`, Not NULL = yes, Primary key = yes. In the column's **Constraints** sub-tab, set Identity = `ALWAYS`.
    - `email`, type `text`, Not NULL = yes
    - `full_name`, type `text`, Not NULL = yes
    - `created_at`, type `timestamp with time zone`, Not NULL = yes, Default = `now()`
4. **Constraints** tab > **Unique** > **+**: add a unique constraint on `email`.
5. Click **Save**. Open the **SQL** tab of the dialog before saving to see the exact statement pgAdmin will run; this is the best way to learn the SQL behind each click.

### Create the rest with the Query Tool

Clicking out every table is slow, so for the rest open **Tools > Query Tool** (with the `shop` database selected), paste the script below and press F5.

```sql
CREATE TABLE IF NOT EXISTS customers (
  customer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       text NOT NULL UNIQUE,
  full_name   text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE categories (
  category_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name        text NOT NULL UNIQUE
);

CREATE TABLE products (
  product_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  category_id bigint NOT NULL REFERENCES categories(category_id),
  sku         text NOT NULL UNIQUE,
  name        text NOT NULL,
  price       numeric(12,2) NOT NULL CHECK (price >= 0),
  active      boolean NOT NULL DEFAULT true
);

CREATE TABLE orders (
  order_id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers(customer_id),
  status      text NOT NULL DEFAULT 'pending'
              CHECK (status IN ('pending','paid','shipped','cancelled')),
  ordered_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  order_id    bigint NOT NULL REFERENCES orders(order_id) ON DELETE CASCADE,
  product_id  bigint NOT NULL REFERENCES products(product_id),
  quantity    integer NOT NULL CHECK (quantity > 0),
  unit_price  numeric(12,2) NOT NULL CHECK (unit_price >= 0),
  PRIMARY KEY (order_id, product_id)
);
```

If you already created `customers` in the GUI, delete its `CREATE TABLE` from the script (or run it as written, since `IF NOT EXISTS` skips it).

### Why these choices

- `order_items.unit_price` copies the price at purchase time. Product prices change; past orders must not. This is deliberate, controlled duplication, not a normalization mistake.
- The composite primary key `(order_id, product_id)` stops the same product appearing twice in one order; a repeat purchase raises `quantity` instead.
- `ON DELETE CASCADE` on `order_items.order_id` removes lines when an order is deleted. Products and customers have no cascade, so you cannot delete one that has orders.
- Foreign keys are not indexed automatically in Postgres; section 6 covers that.

1. Right-click the **shop** database in the tree and choose **ERD For Database**.
2. pgAdmin draws all tables with their columns and foreign-key lines. Drag tables to arrange them.
3. Use the toolbar to **Add table**, **Add/Edit note**, or draw a relationship with **One-to-many** or **Many-to-many** link. Double-click a table to edit columns and keys.

Check that the diagram matches this reading:

| From (many side) | To (one side) | Meaning |
| --- | --- | --- |
| `products.category_id` | `categories` | A category has many products |
| `orders.customer_id` | `customers` | A customer places many orders |
| `order_items.order_id` | `orders` | An order has many lines |
| `order_items.product_id` | `products` | A product appears on many lines |

The last two rows together are the many-to-many relationship between orders and products. If your diagram shows a line from `order_items` to both `orders` and `products`, the model is correct.

The ERD tool is good for exploration and sketching. For a team, keep the real source of truth in versioned SQL migration files (section 6).

### Easy questions

Run each query on its own: select the text and press F5. The answer shows in the **Data Output** tab.

**1. Who are my customers?**

```sql
SELECT * FROM customers;
```

You get 8 rows. `*` means "all columns".

**2. Which products cost less than 100 rupees, cheapest first?**

```sql
SELECT name, price
FROM products
WHERE price < 100
ORDER BY price;
```

Six rows: Potato Chips 20, Marie Biscuits 30, Bath Soap 42, Curd 45, Full Cream Milk 68, Paneer 95.

**3. How many bills are still pending?**

```sql
SELECT count(*) FROM orders WHERE status = 'pending';
```

The answer is 3.

**4. Who placed each bill?** This is your first JOIN: it follows the foreign key from a bill to its customer.

```sql
SELECT orders.order_id, customers.full_name, orders.status
FROM orders
JOIN customers ON customers.customer_id = orders.customer_id
ORDER BY orders.order_id;
```

Twelve rows. Bill 1 belongs to Asha Rao and is shipped.

**5. What is written on bill 1?** Another JOIN, this time from the bill's lines to the product names.

```sql
SELECT products.name, order_items.quantity, order_items.unit_price
FROM order_items
JOIN products ON products.product_id = order_items.product_id
WHERE order_items.order_id = 1;
```

Two rows: Basmati Rice 5kg, 1 at 520.00, and Toor Dal 1kg, 2 at 165.00.

**6. What is the total of bill 1?**

```sql
SELECT sum(quantity * unit_price) AS bill_total
FROM order_items
WHERE order_id = 1;
```

The answer is 850.00 (520 + 2 x 165).

**7. What is the total of every bill?** The same sum, with `GROUP BY` to get one total per bill.

```sql
SELECT order_id, sum(quantity * unit_price) AS bill_total
FROM order_items
GROUP BY order_id
ORDER BY order_id;
```

Totals for bills 1 to 12 are 850, 321, 410, 238, 256, 520, 264, 235, 108, 329, 321 and 290.

**8. Which 3 products sell the most units?**

```sql
SELECT products.name, sum(order_items.quantity) AS units_sold
FROM order_items
JOIN products ON products.product_id = order_items.product_id
GROUP BY products.name
ORDER BY units_sold DESC
LIMIT 3;
```

Full Cream Milk 1L sells 9, Potato Chips 7 and Marie Biscuits 6.

Each statement below should fail with an error. That is the database protecting your data.

```sql
INSERT INTO customers (email, full_name) VALUES ('asha.rao@example.com', 'Dup');  -- email already exists

```

## 6. Indexes, changing the model, and common mistakes

### Index your foreign keys

Postgres indexes primary keys and unique constraints automatically, but not foreign keys. Joins and cascading deletes on those columns need their own index:

```sql
CREATE INDEX idx_orders_customer_id    ON orders(customer_id);
CREATE INDEX idx_products_category_id  ON products(category_id);
CREATE INDEX idx_order_items_product_id ON order_items(product_id);
```

`order_items.order_id` is already covered by the composite primary key. To see whether a query uses an index, prefix it with `EXPLAIN ANALYZE` in the Query Tool; with tiny sample data Postgres will still choose a sequential scan, which is correct.

### Evolve the model with migrations

Models change. Add a shipping address without losing data:

```sql
CREATE TABLE addresses (
  address_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers(customer_id),
  line1 text NOT NULL,
  city  text NOT NULL,
  postal_code text NOT NULL
);

ALTER TABLE orders ADD COLUMN shipping_address_id bigint REFERENCES addresses(address_id);
```

Keep every change like this in numbered `.sql` files (`001_init.sql`, `002_addresses.sql`) under version control, and apply them in order. Tools such as Flyway, Liquibase, Sqitch or your framework's migrations automate this. Postgres runs most DDL inside a transaction, so wrap a migration in `BEGIN; ... COMMIT;` and a failure leaves nothing half-applied.

To run those files automatically on a fresh container, mount a folder into `/docker-entrypoint-initdb.d` on the `db` service (for example `./initdb:/docker-entrypoint-initdb.d:ro`). Files there run only when the data volume is empty, in alphabetical order.

### Common modeling mistakes

| Mistake | Why it hurts | Do this instead |
| --- | --- | --- |
| Comma-separated values in one column | Cannot join, index or constrain them | A child table or junction table |
| `float` for money | Rounding errors | `numeric(12,2)` or integer cents |
| `timestamp` without time zone | Ambiguous moments across servers and users | `timestamptz` |
| Missing foreign keys "for speed" | Orphan rows, silent corruption | Always declare them; index them |
| One table for everything ("god table") | Repeated facts, update anomalies | Split by entity (normalize to 3NF) |
| Enforcing rules only in app code | Every other client can break them | `NOT NULL`, `CHECK`, `UNIQUE`, `REFERENCES` |

## 7. Clean up, practice, and go further

Stop the stack but keep your data:

```bash
docker compose down
```

Delete everything, including the database and pgAdmin settings, to start fresh:

```bash
docker compose down -v
```

Back up the database to a file, or open a `psql` shell, without installing anything locally:

```bash
docker exec pg_modeling_db pg_dump -U app shop > shop_backup.sql
docker exec -it pg_modeling_db psql -U app -d shop
```
